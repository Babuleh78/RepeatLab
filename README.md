# RepeatLab

Java CLI сохраняет исходные ячейки XLSX и формирует воспроизводимый аудит.
Python-пакет агрегирует уже классифицированные строки в заказы и строит историю
и целевую метку по этим заказам. Java clean преобразует проверенный raw-набор
в классифицированные события с полным учётом карантина. Обучение моделей пока не реализовано.
Команда `analyze` сохраняет точные заказы и две SQL-витрины по проверенному clean-набору.

## Установка и проверки

Требуются Git, Eclipse Temurin **25.0.5+8**, uv **0.13.5** и Python **3.12.14**.
Укажите `JAVA_HOME` на каталог JDK и добавьте его `bin` в `PATH`.
Maven Wrapper скачивает Maven **3.10.0** с проверкой SHA-256; системная установка
Maven не нужна. В Windows используйте `./mvnw.cmd`, в Linux/macOS — `sh ./mvnw`.

```text
uv python install
sh ./mvnw -B -f java/pom.xml verify
uv sync --locked --dev
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy src tests
uv run --locked pytest
uv build --no-sources
```

На Windows весь набор проверок запускается командой `./scripts/check.ps1`.
Если uv установлен через WinGet, скрипт найдёт его и при отсутствии команды в PATH.
Установка закреплённой версии:

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/0.13.5/install.ps1 | iex"
```

После установки откройте новый терминал и проверьте `uv --version`.
[Инструкция установки uv](https://docs.astral.sh/uv/getting-started/installation/).

## Загрузка и аудит XLSX

```text
java -jar java/target/repeatlab-data.jar --help
java -jar java/target/repeatlab-data.jar ingest --input data/raw/source.xlsx --output data/processed/run-001
```

Родительский каталог output должен существовать, сам output должен быть новым.
CLI не скачивает исходники. Встроенный профиль `online-retail-v1` соответствует
колонкам [Online Retail II, Daqing Chen (2012)](https://doi.org/10.24432/C5CG6D),
лицензия [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).
[Страница источника и загрузки](https://archive.ics.uci.edu/dataset/502/online+retail+ii).
Примеры и тесты проекта используют только синтетические значения; фактические
свойства реального файла необходимо устанавливать собственным аудитом.

| Exit code | Результат |
|---|---|
| `0` | Аудит завершён; возможны предупреждения |
| `2` | Аудит завершён с ошибками значений; все строки сохранены |
| `1` | Ошибка файла, структуры или записи; завершённого набора нет |
| `64` | Неверная команда или аргументы |

Все листы, в том числе скрытые и пустые, обрабатываются в порядке книги.
Первый непустой физический ряд каждого листа считается заголовком. Обязательны
`Invoice`/`InvoiceNo`, `StockCode`, `Description`, `Quantity`, `InvoiceDate`,
`Price`/`UnitPrice`, `Customer ID`/`CustomerID`, `Country`. Алиасы точные,
регистрозависимые; пробелы не удаляются. Два алиаса одного поля или отсутствие
обязательного поля на непустом листе — ошибка структуры. Дополнительные столбцы,
пустые ячейки заголовка и пустые листы допустимы.

Поддерживаются незашифрованные transitional OOXML `.xlsx` с обычными worksheet,
shared/inline strings и скалярными ячейками. XLS, XLSB, strict OOXML, chart sheets,
DTD и внешние XML entities не входят в профиль. Формулы не вычисляются, внешние
ссылки не загружаются. Форматирование и rich-text стили не воспроизводятся;
текстовые фрагменты объединяются с сохранением пробелов, индекс стиля сохраняется.
Исходная книга остаётся неизменной и нужна для полного восстановления оформления.

## Контракт артефактов загрузки

JSON/JSONL имеет `schema_version: 1`, UTF-8 без BOM и LF. Числовые значения ячеек
сохраняются **строками** из XML: `0.1000` не становится `0.1`, а текстовый ID
`00042` не становится числом. Порядок листов, строк, столбцов и диагностик фиксирован.

| Файл | Содержание |
|---|---|
| `raw_transactions.jsonl` | По записи на физический XML-ряд, включая заголовки и пустые ряды |
| `issues.jsonl` | Код, severity, источник, координаты, исходная ячейка, сообщение и связанная строка дубля |
| `audit.json` | Схемы/численности листов, проблемы, пропуски, число различных ключей и диапазон дат |
| `manifest.json` | Маркер завершения, версии, параметры, источник и hashes воспроизводимых артефактов |
| `run.json` | Время исполнения и версия JVM; не входит в воспроизводимые hashes |

Raw-запись содержит `source_sha256`, `sheet_index` (от 1), `sheet_name`,
`row_number` (от 1), `kind` (`header`, `data`, `empty`) и массив `cells`.
Номера отсутствующих рядов не материализуются: пропуски до последнего физического
ряда считаются в `absent_rows`. `physical_rows`, `header_rows`, `data_rows`,
`empty_rows`, видимость листа и соответствие полей столбцам записаны в manifest/audit.

Каждая ячейка содержит:

- `column`, `reference`: буква столбца и координата, например `F`, `F3`;
- `source_type`: OOXML `n`, `s`, `inlineStr`, `str`, `b`, `e`, `d`; при отсутствии `t`
  используется его стандартное значение `n`; у отсутствующей ячейки — `null`;
- `state`: `missing`, `blank`, `empty_string`, `value` или `formula`;
- `value`: текст или точная числовая строка; для формулы — `null`;
- `raw_value` хранит исходный текст XML `v`, включая индекс shared string и cache.
  Для inline-строки с Excel-последовательностью экранирования сохраняется также
  объединённый исходный текст до декодирования;
- `style`: исходный индекс стиля либо `null`;
- `formula`: текст формулы в `text` и исходные атрибуты (`t`, `si`, `ref` и другие),
  либо `null`; `cached_value`: разрешённое сохранённое значение формулы либо `null`.

Отсутствующие ячейки добавляются до ширины заголовка или текущей строки.
Отсутствующая ячейка, физически пустая ячейка и строка нулевой длины различимы.
Ведущие/конечные пробелы и Unicode-пробелы не очищаются. Rich text сохраняется как
объединённый текст без фонетических аннотаций. Строка с одними пустыми значениями
имеет `kind: empty` и сохраняется, но не считается транзакцией для проверок типов.

Неразбираемые или отсутствующие quantity/price/date — ошибки данных. Quantity
должно быть целым; price — конечным десятичным числом; числовые строки разрешены,
boolean/error ячейки недопустимы для этих полей. Неположительная цена, нулевое
количество, несогласованность префикса `c`/`C` со знаком количества, отсутствующие
ключи и возможные дубли — предупреждения. Отсутствующий customer ID не заменяется.
Каждая формула получает предупреждение; её cache не участвует в проверках типов,
знаков, ключей или диапазона дат. Формула в заголовке — ошибка структуры.

Даты проверяются как Excel serial с системой `1900`/`1904` из книги либо ISO local
`YYYY-MM-DD` / `YYYY-MM-DDTHH:mm:ss[.fraction]` без offset. Часовой пояс не назначается.
Serial 60 в системе 1900 (фиктивное 29 февраля) и отрицательные serial недопустимы;
serial 0 означает 1899-12-31 или 1904-01-01. Диапазон дат ограничен годом 9999.
В новых raw-наборах (`tool_version: 0.1.1`) допустимость даты проверяется
до округления. Для сводного диапазона время округляется до наносекунд с HALF_UP.
Последний момент года 9999 отображается максимум как `23:59:59.999999999`.
Форматы shared, inline и str используют одинаковое декодирование Excel-строк.
При чтении raw 0.1.0 воспроизводится аудит версии, создавшей набор. Чтобы получить
исправленные значения строк и сводку дат, повторите ingest исходного XLSX в новом каталоге.
Исходная числовая строка не меняется. Денежные значения не округляются и не
преобразуются через `double`.

Возможный дубль сравнивается по каноническим полям и дополнительным столбцам,
типам, состояниям, исходным значениям и формулам, включая разные листы.
Координаты строки и индексы стилей не входят в сравнение; shared string сравнивается
по разрешённому тексту. Числа и строки не нормализуются. Для дополнительных
столбцов учитывается позиция. Повторные записи сохраняются, `related_row` указывает
на первое совпадение. SHA-256 fingerprints используются для сравнения; это
диагностика возможных дублей, а не правило удаления. `distinct_keys` также считает
различные представления ключа, без приведения числовых ID к текстовым.

Только `manifest.json` со `status: completed` и совпадающими SHA-256 из `artifacts`
обозначает готовый набор. `data_status` (`ok`, `warnings`, `errors`) отдельно описывает
качество данных. Manifest содержит basename и SHA-256 входа, версии CLI/профиля,
систему дат, параметры и их hash, листы и hashes raw/issues/audit. Пути и время
не входят в эти артефакты; manifest не хеширует себя. Одинаковые байты исходника,
basename и параметры дают одинаковые raw/issues/audit/manifest.

Каталог резервируется атомарно без перезаписи. Запись выполняется в `.partial`,
файлы закрываются и hashes проверяются, затем manifest публикуется последним
атомарным переименованием. Если файловая система не поддерживает это действие,
запуск завершается ошибкой. При обрабатываемой ошибке команда удаляет свои
промежуточные файлы и записывает этап и причину в `fatal.json` и stderr.
При ошибке листа в stderr выводятся его номер и номер строки, а название листа
сохраняется в локальном `fatal.json`. Если запись в каталог недоступна,
диагностику можно прочитать в stderr. Новый каталог результата на POSIX
доступен только владельцу (0700). На Windows права задаёт ACL родителя.
После принудительной остановки процесса или ошибки удаления проверьте
оставшиеся файлы и укажите новый каталог для следующего запуска.

Команды принимают ссылку на выбранный каталог набора, книгу XLSX или файл
конфигурации. Внутри raw, clean и orders каждый именованный входной файл,
включая manifest, должен быть обычным файлом. Ссылки и специальные файлы
отклоняются перед чтением. Размещайте входные и выходные каталоги там,
где другие процессы не могут подменять их содержимое во время запуска.

Чтение worksheet потоковое. Таблица shared strings, fingerprints дублей и
различных ключей занимают память пропорционально числу уникальных значений;
копия входного файла в `.partial` обеспечивает чтение и hash одних байтов.
Команда проверяет тип основной части XLSX и связи книги с листами и таблицей
общих строк. Повторное поле значения или формулы в одной ячейке завершает
чтение ошибкой. Готовый raw передаётся на отдельный этап очистки.

## Агрегация заказов

`aggregate_orders` принимает последовательность или генератор `CleanEvent`.
Каждая запись содержит строковые `event_id`, `invoice_id`, `stock_code`,
`customer_id` (строка или `None`), `event_time` (datetime без часового пояса),
`kind` (`sale` или `cancellation`), целое `quantity` и цену `unit_price` типа
`Decimal`. Количество положительно для продажи и отрицательно для отмены;
цена конечна и строго положительна. Неверные типы, знаки, `float`-цены и
timezone-aware даты отвергаются. Идентификаторы сохраняются без преобразований.

```python
from datetime import datetime
from decimal import Decimal

from repeatlab.aggregation import CleanEvent, aggregate_orders
from repeatlab.temporal import build_snapshot

events = (
    CleanEvent(
        "e1", "invoice-1", "A", datetime(2010, 12, 10), "sale", "product-1", 2, Decimal("1.25")
    ),
    CleanEvent(
        "e2", "invoice-1", "A", datetime(2010, 12, 10), "sale", "product-2", 1, Decimal("0.335")
    ),
)
result = aggregate_orders(events, service_codes={"DELIVERY"})
order = result.orders[0]
assert (order.line_count, order.quantity, order.stock_code_count) == (2, 3, 2)
assert order.total_amount == Decimal("2.835")

snapshots = build_snapshot(
    (order.to_temporal_order() for order in result.orders),
    snapshot_time=datetime(2011, 1, 1),
    observed_until=datetime(2011, 2, 1),
)
assert snapshots[0].history_order_count == 1
```

Один согласованный счёт даёт один `AggregatedOrder`: ключ счёта, покупатель,
время, вид события, число товарных строк, сумма единиц, число различных товарных
кодов и точная сумма `quantity × unit_price`. Округления нет, включая цены с
долями копейки; вычисление не зависит от precision, rounding и traps текущего
Decimal-контекста. Количество и сумма отмен остаются отрицательными. Отмены
сохраняются отдельными счетами и не вычитаются из предыдущих продаж.

Точный итог должен быть представим конечным значением `Decimal`. По умолчанию
коэффициент суммы одного заказа ограничен 100 000 десятичными цифрами при
сохранении исходной точности. Предел задаётся положительным целым в переменной
окружения `REPEATLAB_MAX_ORDER_AMOUNT_DIGITS` для Python API и процессов,
запускаемых командами `analyze` и `duplicate-sensitivity`. При пределе 5
сумма `10000 + 0.01` требует семи цифр и завершает расчёт ошибкой. Отдельное
значение `1E+500` укладывается в этот предел с коэффициентом 1. Ограничения
SQL на тип DECIMAL проверяются отдельно. Превышение предела или диапазона
`Decimal` вызывает `ValueError`. Настройки и флаги Decimal-контекста
вызывающего кода сохраняются, включая случай ошибки.

Результат содержит неизменяемые кортежи заказов и диагностики:

- `excluded_service_event_ids`: строки с кодами из явно переданного
  `service_codes` (по умолчанию пусто). Они не входят в число строк, единиц,
  товаров и сумму; служебный счёт без товаров не создаёт заказ.
- `possible_duplicate_event_ids`: группы ID строк с одинаковыми полями, кроме
  `event_id`, среди всех входных событий. Такие строки сохраняются. Повторение
  самого `event_id` вызывает `ValueError` для всего входа, даже если строка
  служебная или относится к конфликтному счёту.
- `quarantined_invoices`: счета с разными `customer_id`, `event_time` или `kind`.
  Каждая запись содержит `invoice_id`, имена конфликтующих полей и все исходные
  события. Проверка выполняется до фильтрации служебных кодов; строки карантина
  не дублируются в `excluded_service_event_ids`. Остальные счета обрабатываются.

Сочетание `None` и известного покупателя внутри счёта — конфликт. Если все ID
покупателя отсутствуют, заказ сохраняется с `customer_id=None`; адаптер
`to_temporal_order()` передаёт его без подстановки фиктивного клиента.
Заказы и карантин упорядочены по счёту, ID внутри диагностики — по строковому
порядку. Перестановка входных строк не меняет результат.

Агрегатор принимает классифицированные события и не загружает исходные файлы.
Для готового clean-набора используйте read_clean_dataset: проверка префикса счёта
выполняется при очистке и проверенном чтении. Коллизии номеров
счетов не исправляются составным ключом. Тест с синтетическим JOIN проверяет
отклонение размноженных `event_id` на входе агрегации; общего API для JOIN нет.
Агрегация выполняется в памяти, поэтому объём входа и размер точных десятичных
чисел ограничены доступными ресурсами.

## Временной контракт

`build_snapshot` принимает валидированные заказы, момент расчёта и явный конец
наблюдения. В историю входят покупки за предыдущие 180 дней, строго до момента
расчёта. Цель учитывает покупки в следующие 30 дней: левая граница включена,
правая исключена. Оба окна задаются положительным целым числом дней.

Покупатели без известного ID и без покупок в прошлом окне не включаются.
Отмена не считается покупкой. При неполном горизонте строка получает
`status="censored"` и `label=None`; её нельзя использовать как отрицательный исход.
Даты сохраняются в исходной временной шкале без назначения часового пояса.

Для снимка из реального журнала запустите `snapshot` на готовом **raw**. Команда
проверяет исходный набор и применяет конфигурацию очистки к строкам, доступным
на соответствующую дату. Временем доступности служит время события.

```text
java -jar java/target/repeatlab-data.jar snapshot --input data/processed/run-001 --config configs/cleaning.json --snapshot-time 2011-01-01T00:00:00 --observed-until 2011-02-01T00:00:00 --output data/processed/snapshot-001
```

Для истории счёт проверяется по всем датированным строкам строго до снимка.
Для метки — до конца горизонта или указанного конца наблюдения, если он раньше.
Например, мартовская коллизия январского счёта оставляет покупку в истории
на 1 февраля. Та же коллизия внутри окна метки исключает конфликтный счёт
из расчёта метки. Окна по умолчанию равны 180 и 30 дням. Их задают
`--lookback-days` и `--horizon-days`. Конец горизонта должен помещаться в 0001–9999.

`snapshots.jsonl` содержит по строке на известного покупателя с покупкой в истории.
Поля — `customer_id`, `snapshot_time`, `history_order_count`, `label_end`, `label`
и `status`. При неполном наблюдении `label` равен `null` для всей аудитории.
`manifest.json` фиксирует вход, конфигурацию, окна и хеш результата. Строки
с неразбираемой датой пропускаются и учитываются в `counts.undated_rows` по всей
выгрузке. При таких строках или карантине команда публикует проверенный результат
и возвращает 2. Полный отчёт по всем счетам по-прежнему строится командой `clean`.

Искусственные данные находятся в `data/fixtures/`, проверки — в `tests/`.
Большие исходные и обработанные данные не хранятся в Git.

## Очистка и проверенное чтение

```text
java -jar java/target/repeatlab-data.jar clean --input data/processed/run-001 --config configs/cleaning.json --output data/processed/clean-001
```

Команда проверяет завершённый ingest-набор, копирует входные артефакты в закрытый
рабочий каталог, сверяет hashes скопированных байтов и читает именно эту копию.
XLSX повторно не читается. Непригодные значения из завершённого raw-набора с
`data_status=errors` диагностируются построчно. Выходной каталог должен быть новым.

Политика `clean-v1`: sale требует положительных quantity/price и счёта без префикса
`c`/`C`; cancellation требует отрицательного quantity, положительной price и этого
префикса. Знаки и значения не исправляются. Непригодная строка изолирует весь
определимый счёт, включая его служебные позиции. Неопределимый invoice изолирует
только собственную строку. Разные customer/time/kind также изолируют весь счёт;
точные моменты сравниваются до сокращения точности. Дубли содержимого сохраняются.

Числовой ID должен быть точным целым: `42.0` и `4.2E1` становятся `"42"`.
Непустой текст сохраняется буквально, включая ведущие нули и пробелы. Отсутствующий,
пустой или состоящий только из Unicode White_Space customer становится `null`;
обязательные invoice/stock в таком случае непригодны. White_Space здесь означает
U+0009–000D, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028–2029,
U+202F, U+205F, U+3000. Формулы в необходимых полях не имеют доверенного значения;
формулы только в description/country не блокируют событие.

Деньги передаются точной десятичной строкой, количество — JSON integer.
Время вычисляется напрямую из точного serial/ISO без `double` и округления аудита;
результат floor до микросекунды остаётся в прежнем дне на `23:59:59.9999996`.
Реальная потеря точности отмечается флагом. Поддерживаются годы 1–9999 без timezone,
системы Excel 1900/1904; фиктивный день serial60 исключён. Субмикросекундный порядок
теряется в clean, исходная точность остаётся доступна через происхождение в raw.

Конфигурация содержит ровно `policy_version: "clean-v1"` и массив строк
`service_codes`. Пустой массив допустим; никакой список кодов не угадывается.
Коды имеют буквальный смысл. Повторы устраняются, порядок канонизируется по Unicode
code point. Канонический JSON имеет отсортированные ключи, UTF-8 без BOM,
без незначащих пробелов и без ASCII-экранирования Unicode. Control escapes имеют
строчные hex-цифры, стандартные \b, \f, \n, \r, \t сохраняются; hash конфигурации — SHA-256
этих байтов без завершающего LF. Версия политики включена в hash. Неизвестные поля,
неверные типы и повторные JSON-ключи отклоняются.

Clean-артефакты используют `schema: "repeatlab-clean"`, `schema_version: 1`:

| Файл | Содержание |
|---|---|
| `clean_events.jsonl` | Восемь полей CleanEvent, provenance, quality_flags и is_service; включает принятые служебные строки |
| `dispositions.jsonl` | Ровно один outcome каждой raw data-строки: accepted_product, accepted_service или quarantined, причины и flags |
| `audit.json` | Полное покрытие, принятые/карантинные строки, отсутствующие customer, header/empty, counts причин |
| `manifest.json` | Завершение, версии, hashes входа и артефактов, каноническая конфигурация, counts и качество |
| `run.json` | Изменчивые сведения исполнения вне воспроизводимых hashes |

`is_service` согласован с конфигурацией; это флаг, отдельный от kind.
`provenance` содержит source_sha256, sheet_index, sheet_name, row_number.
`event_id` равен SHA-256 UTF-8 строки `source_sha256:sheet_index:row_number` с обычными
десятичными координатами. Он не зависит от классификации, содержимого или конфигурации.
Порядок записей — исходный порядок листов/строк; ключи JSON и массивы flags/reasons
сортируются. Собственная ошибка строки отличается от `INVOICE_INVALID`, применяемой
ко всем строкам неполного счёта, и `INVOICE_CONFLICT_*` для конфликта полей.

Exit0 означает completed без карантина (предупреждения допустимы); exit2 — completed
с карантином и пригодным подмножеством. Exit1 — ошибка набора/структуры/записи, exit64 —
неверный запуск. Manifest публикуется последним атомарно. При ошибке завершённого
manifest нет, по возможности сохраняется fatal.json. Никакой output не перезаписывается.

```python
from repeatlab.cleaning import read_clean_dataset

dataset = read_clean_dataset("data/processed/clean-001")
result = dataset.aggregate()
```

Reader проверяет весь набор до выдачи событий: версии, hashes, конфигурацию,
происхождение, уникальность, dispositions, counts и согласованность счетов.
Один файл событий без manifest не является проверенным набором. Возвращаются
неизменяемые события/коды/метаданные; цена — Decimal, время — naive datetime.
`dataset.aggregate()` передаёт согласованные service_codes в существующий агрегатор,
чтобы служебные строки не попали в суммы по умолчанию. Дальнейший snapshot использует
прежний явный observed_until и неизменённые временные границы.

Java хранит в памяти состояние счетов и происхождения, а ячейки обрабатывает потоково.
Python читает JSONL построчно и держит в памяти принятые события и индексы проверки. SHA-256 проверяет целостность,
но не является подписью автора: источник набора должен быть доверенным. Объединение
нескольких raw-наборов и автоматическое исправление коллизий invoice не поддерживаются.

## Заказы и SQL-аналитика

После сборки JAR и `uv sync --locked --dev` запустите:

```text
java -jar java/target/repeatlab-data.jar analyze --input data/processed/clean-001 --python .venv/bin/python --output data/processed/analytics-001
```

На Windows укажите `--python .venv/Scripts/python.exe`. Требуется Python 3.12 с
установленным пакетом RepeatLab. Java запускает его напрямую с `-I`: пакет выбирается
из окружения указанного интерпретатора независимо от текущего каталога и `PYTHONPATH`.
Запуск обходится без shell и установки зависимостей во время анализа.
Отдельный worker доступен как
`python -m repeatlab.orders --input <clean-dir> --output <new-orders-dir>`.

Worker вызывает существующую агрегацию проверенного clean-набора. В `orders/` остаются
`orders.jsonl`, `lineage.jsonl`, `duplicates.jsonl`, `audit.json` и завершённый
`manifest.json`. Ключ заказа — буквальный invoice_id в одном входном наборе.
Quantity остаётся точным JSON integer, деньги — точной десятичной строкой.
Lineage содержит каждую принятую строку: товарную с ключом заказа или служебную с
`order_key: null`. Счёт только со служебными строками не создаёт заказ.
Дубли сохраняются; группы возможных дублей включают и служебные строки.

Java проверяет версии, строгую JSON-схему, SHA-256, порядок записей, численности и
принадлежность lineage той же частной копии clean, которую получил worker.
Перед публикацией `orders/` Java сверяет состав групп дублей и точные суммы по
товарным строкам каждого счёта. Заказы становятся доступны одним атомарным
перемещением после проверки и остаются доступными при последующем отказе SQL.
Неполное или изменённое содержимое не считается завершённым обменом. SHA-256
проверяет целостность, а не подлинность производителя.

Встроенный DuckDB выполняет репозиторные запросы `sql/monthly_activity.sql` и
`sql/missing_customer.sql`, упакованные в JAR. База существует только в памяти;
результаты публикуются как стабильные UTF-8 JSONL:

| Файл | Показатели |
|---|---|
| `monthly_activity.jsonl` | Месяц, kind, заказы, различные известные покупатели, товарные строки и точные суммы для всех/известных/отсутствующих customer |
| `missing_customer.jsonl` | Числа заказов и товарных строк, суммы без customer и их точные доли |
| `audit.json` | Численности orders и исходного clean, качество, число строк витрин, выбранный scale |
| `manifest.json` | Готовность, качество, входные hashes, версия DuckDB, scale, hashes SQL и результатов |

Месяц сохраняет исходную naive временную шкалу. Продажи и отмены идут раздельно,
со своими знаками; это не прибыль и не net revenue. Отсутствующий customer не
становится фиктивным общим покупателем. Знаменатели долей включают только принятые
товарные заказы/строки после настройки service_codes, включая сохранённые дубли.
Исходный карантин показан отдельно и не входит в эти знаменатели. Доли — объекты
`{"numerator": ..., "denominator": ...}`; нулевой знаменатель даёт `null`.
Пустой товарный набор не создаёт искусственных месяцев или границ наблюдения.

SQL использует `DECIMAL(38,s)`: общий scale выбирается после удаления незначащих
конечных нулей. Значение `0.335` остаётся точным, а `0.7350` может записаться как
`0.735`. Scale больше 38, коэффициент шире 38 цифр, переполнение групповой суммы
или SQL-счётчика явно завершают аналитику с ошибкой. Округления и перевода в
карантин нет. Завершённые точные orders остаются пригодны для последующей работы.
Quantity не загружается в SQL и не ограничивается размером машинного целого.

DuckDB настроен на `memory_limit=1GB`, `threads=1`, с частным temp-каталогом внутри
нового output. Это лимит движка, а не гарантия общего RAM процесса: Python и Java
хранят проверенные события/заказы в памяти. Двоичная база не публикуется.
`run.json`, `worker.stdout.log`, `worker.stderr.log`, при ошибке `fatal.json`
содержат диагностику вне стабильных hashes. Внешний manifest публикуется атомарно
последним. Exit0 — completed, exit2 — completed с унаследованным карантином,
exit1 — ошибка этапа, exit64 — неверные аргументы. Существующий output не заменяется.

Для `analyze` и `duplicate-sensitivity` время Python-процесса по умолчанию
ограничено одним часом. Для двух часов укажите `-Drepeatlab.worker.timeoutSeconds=7200`
перед `-jar`. Каждый из двух логов хранит первые 2 МиБ и отметку об усечении.
При очистке числовых ID и количеств предел по умолчанию составляет 100 000 цифр
на одно развёрнутое целое. Для другого предела задайте положительное
`-Drepeatlab.clean.maxIntegerDigits=200000`. Превышение завершает `clean`
или `snapshot` с диагностикой, исходная запись сохраняется в raw.

JDBC закреплён как `org.duckdb:duckdb_jdbc:2.0.0.1` (движок DuckDB 2.0.0),
лицензия MIT. JAR содержит лицензии/уведомления зависимостей в META-INF; упаковка
сохраняет notices POI/Jackson. Точные тексты лицензий
[JDBC v2.0.0.1](https://github.com/duckdb/duckdb-java/blob/v2.0.0.1/LICENSE) и
[движка v2.0.0](https://github.com/duckdb/duckdb/blob/v2.0.0/LICENSE) включены отдельно
в `META-INF/licenses/` вместе с `duckdb-SOURCES.txt`, поскольку upstream JDBC JAR
не содержит этих текстов. Copyright и permission notice сохранены без изменений.
Отдельных Python-зависимостей для SQL нет.

## Повторные покупки и активность когорт

Передайте каталог с завершённым набором заказов. Команда проверяет копию входных
артефактов и выполняет два SQL-запроса во встроенном DuckDB. Ей достаточно
`orders/` из `analyze` или каталога, созданного `repeatlab.orders`. Заказы
пригодны для расчёта когорт и после ошибки денежной витрины, если у них есть
завершённый manifest.

```text
java -jar java/target/repeatlab-data.jar cohorts --input data/processed/analytics-001/orders --observed-from 2020-01-01T00:00:00 --observed-until 2020-04-15T00:00:00 --output data/processed/cohorts-001
```

Границы задаёт оператор в исходной шкале журнала. Формат — `YYYY-MM-DDTHH:mm:ss`
с годом от 0001 до 9999, необязательной дробной частью до микросекунд и без
часового пояса. Начало включено, конец исключён. Любой заказ вне интервала,
включая отмену или заказ без клиента, останавливает расчёт.

- `repeat_rates.jsonl` содержит число клиентов, число клиентов с полным периодом,
  число клиентов с неполным периодом, число повторивших покупку и долю за 30, 60
  и 90 дней. Повтором считается продажа строго позже первой наблюдаемой продажи
  и строго раньше конца горизонта. Счета с одинаковым временем сами по себе
  повтора не образуют. Горизонт полный, если время первой продажи плюс число
  дней не позже `observed-until`. Клиенты с неполным горизонтом остаются вне
  числителя и знаменателя, даже если следующая покупка уже наблюдалась.
- `cohort_activity.jsonl` группирует клиентов по месяцу их первой наблюдаемой
  продажи. Возраст когорты начинается с 0. Активным считается клиент с хотя бы
  одной продажей за месяц, включая первую продажу в месяце 0. В полном месяце
  без продаж число активных равно 0. Для частичного первого или последнего
  месяца число активных и доля равны `null`, статус — `censored`. Месяцы за
  концом интервала не выводятся.

Обе витрины учитывают товарные продажи с известным клиентом. Доли передаются
точными парами `{"numerator": ..., "denominator": ...}`. При нулевом знаменателе
доля равна `null`. При пустом множестве клиентов остаются три строки горизонтов,
а файл активности пуст. Дата первой наблюдаемой продажи зависит от предоставленного
набора и его покрытия.

Файлы используют `repeatlab-cohorts` версии 1. В `audit.json` сохранены покрытие,
исходные счётчики, качество данных и числа строк витрин. Завершённый `manifest.json`
связывает результаты с хешами входного набора, SQL и файлов результатов. Каталог
результата создаётся один раз. Код 0 означает готовый результат, 2 — готовый
результат с унаследованным карантином, 1 — ошибку данных или выполнения, 64 —
неверный вызов. При коде 1 завершённый manifest не публикуется.

## Интервалы между покупками и концентрация продаж

Команда `sales-profile` принимает завершённый набор заказов из `analyze` или
`repeatlab.orders`. Она проверяет копию входных артефактов и выполняет запросы
`sql/purchase_intervals.sql` и `sql/sales_concentration.sql` из JAR в одной
транзакции DuckDB.

```text
java -jar java/target/repeatlab-data.jar sales-profile --input data/processed/analytics-001/orders --observed-from 2020-01-01T00:00:00 --observed-until 2020-04-01T00:00:00 --output data/processed/sales-profile-001
```

Как и в `cohorts`, границы обязательны и задаются в исходной шкале журнала,
без часового пояса, с секундами и необязательной дробной частью до шести знаков.
Начало должно предшествовать концу. Начало включено, конец исключён. Любой заказ
вне интервала останавливает расчёт, включая отмену или заказ без клиента.

- `purchase_intervals.jsonl` содержит две строки — `first` для интервала между
  первыми двумя наблюдаемыми покупками клиента и `later` для последующих интервалов.
  Счета одного клиента с одинаковым временем образуют один момент покупки.
  Для каждого сегмента выводятся число интервалов, число клиентов, минимум и
  максимум в микросекундах и распределение по диапазонам `[0, 1)`, `[1, 7)`,
  `[7, 30)`, `[30, 90)` и от 90 дней. Для пустого сегмента счётчики равны нулю,
  минимум и максимум равны `null`. В расчёт входят только пары последовательных
  наблюдаемых покупок с известным клиентом.
- `sales_concentration.jsonl` содержит строки для верхних 1%, 5% и 10% клиентов
  по сумме положительных продаж. Число клиентов в каждой группе равно
  `ceil(p × N / 100)`, где `N` — число известных клиентов хотя бы с одной продажей.
  При равенстве сумм квота сохраняется. Каждый счёт участвует в суммах, в том числе
  при совпадении времени. Продажи без клиента входят только в сумму всех продаж.
  Суммы записываются точными десятичными строками, доли — парами
  `{"numerator": ..., "denominator": ...}`. При нулевом знаменателе доля равна
  `null`. Ранжирование описывает весь заявленный интервал.

Отмены проходят проверку входа и покрытия. Обе витрины и выбор масштаба `DECIMAL`
используют только продажи. Если сумму или её масштаб нельзя представить точно,
команда завершается с ошибкой этапа `sql`. Входные заказы остаются доступными
для `cohorts`.

Витрины, `audit.json` и `manifest.json` используют схему `repeatlab-sales-profile`
версии 1. Аудит содержит покрытие, исходные счётчики, качество, масштаб и числа
строк двух витрин. Завершённый manifest связывает входные хеши, версию движка,
масштаб, хеши SQL и хеши результатов. Новый каталог создаётся вне входного набора
заказов. Коды выхода совпадают с `cohorts`. При ошибке подробности сохраняются
в `fatal.json`, если каталог результата удалось создать.

## Повторные товары в заказе

Команда `product-repeats` показывает для каждого положительного товарного заказа
известного покупателя, сколько разных товарных кодов он уже покупал раньше.
Передайте завершённые заказы и тот очищенный журнал, из которого они собраны.
Команда сверяет хеши копий обоих наборов и связывает товарные строки с заказами
по `event_id` и `order_key`. Затем встроенный DuckDB выполняет `sql/product_repeats.sql`.

```text
java -jar java/target/repeatlab-data.jar product-repeats --input data/processed/analytics-001/orders --clean data/processed/clean-001 --observed-from 2020-01-01T00:00:00 --observed-until 2020-04-01T00:00:00 --output data/processed/product-repeats-001
```

`product_repeats.jsonl` содержит по строке на заказ в порядке `order_key`,
с идентификатором покупателя `customer_id` и исходным временем `event_time`.
Знаменатель `distinct_products` учитывает каждый товарный код в счёте один раз.
Числитель `repeated_products` считает коды из этого счёта, встречавшиеся в
строго более ранних положительных заказах того же покупателя.

| Наблюдаемая история покупателя | Текущий счёт | `has_prior_purchase` | `repeat_share` |
| --- | --- | --- | --- |
| Первый наблюдаемый момент покупки | A, B | `false` | `null` |
| Ранее купил A | A, A, A, B | `true` | `{"numerator":1,"denominator":2}` |
| Ранее купил A | B, C | `true` | `{"numerator":0,"denominator":2}` |

В первом наблюдаемом заказе сохраняются число разных товаров и нулевой
`repeated_products`. У каждого из двух счетов в один момент одна и та же
предшествующая история. Позднейшая отмена сохраняет прежнюю покупку в истории.
Служебные позиции исключены из состава заказа. Анонимные продажи и отмены
проходят проверку покрытия и остаются вне персональной витрины.

Интервал `[observed-from, observed-until)` задаётся в исходной шкале журнала,
с точностью до микросекунд. Любой заказ вне заявленного интервала останавливает
расчёт. Для пустой выборки файл витрины пуст, а число строк в `audit.json`
равно нулю. Витрина, аудит и завершённый `manifest.json` используют схему
`repeatlab-product-repeats` версии 1. Манифест связывает результат с хешами обоих
входных манифестов, SQL и файлов результата. Укажите новый каталог вывода вне обоих
входных наборов. Код 0 означает успешную публикацию, 2 — публикацию с унаследованным
карантином, 1 — ошибку данных или выполнения, 64 — ошибку аргументов.

## Влияние возможных дублей на месячные показатели

Команда `duplicate-sensitivity` принимает готовый clean-набор и сравнивает два
расчёта на одних и тех же заказах. Нужен Python 3.12 с установленным пакетом
RepeatLab. В Windows путь к интерпретатору обычно `.venv/Scripts/python.exe`.
Используйте JAR и Python-пакет из одной версии. Java сверяет хеши входа и
файла расчёта из ответа Python и проверяет оба сценария по строкам каждого счёта.

```text
java -jar java/target/repeatlab-data.jar duplicate-sensitivity --input data/processed/clean-001 --python .venv/bin/python --output data/processed/duplicate-sensitivity-001
```

В сценарии `retained` учитываются все принятые товарные строки. В сценарии
`collapsed` каждая группа возможных дублей учитывается один раз. Группа определяется
семью полями очищенного события — счётом, покупателем, временем, типом операции,
кодом товара, количеством и числовой ценой. Например, цены `10.0` и `10.00`
равны для группировки. Совпадение всех полей показывает, как могло бы измениться
значение показателя, если повторная запись была лишней. Оба сценария читают одну
копию исходного набора. Служебные позиции и строки карантина исключаются из обоих
расчётов.

В `duplicate_sensitivity.jsonl` одна запись на наблюдаемое сочетание календарного
месяца (`month`), типа заказа (`kind`, продажа или отмена) и наличия идентификатора
покупателя (`customer_known`). Поля `retained` и `collapsed` содержат четыре показателя.

| Показатель | Смысл |
| --- | --- |
| `order_count` | Число заказов. Каждый счёт даёт один заказ в обоих сценариях. |
| `product_line_count` | Число учтённых товарных строк. |
| `units` | Сумма количества единиц товара, записанная строкой целого числа. |
| `amount` | Сумма произведений количества на цену, записанная точной десятичной строкой. |

Например, в одном январском заказе без ID две одинаковые строки по 3 единицы с
ценой 2. Для январских продаж без ID получится 1 заказ в каждом сценарии,
2 и 1 товарная строка, 6 и 3 единицы, суммы 12 и 6 соответственно.
Для отмен количества и суммы сохраняют отрицательный знак. При пустом
товарном наборе файл витрины пуст.

`audit.json` содержит качество и счётчики исходного набора, число заказов и
строк витрины, общее число товарных строк в каждом сценарии.
`manifest.json` со статусом `completed` фиксирует схему
`repeatlab-duplicate-sensitivity` версии 1 и хеши входного манифеста,
конфигурации очистки, входных файлов, SQL и выходных артефактов. Для денег
действует граница точного представления DuckDB `DECIMAL(38,s)`. Если значение
или результат суммирования выходит за границу, запуск завершается ошибкой.
Укажите новый каталог результата вне входного набора. Коды выхода —
0 для готового результата, 2 при унаследованном карантине, 1 при ошибке
данных или выполнения и 64 при неверном вызове.
